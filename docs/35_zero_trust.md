# 35. ゼロトラストの考え方と、このアプリの診断・実装

## ゼロトラストとは

「社内の中だから安全」「ログインしているから安全」と**暗黙に信用しない**考え方です。ネットワークの場所や、過去のログインではなく、**リクエストのたびに**「誰が・どの端末で・何に対して・してよいか」を確かめ、**侵害されている前提**で被害を小さくします。

- **NIST SP 800-207（Zero Trust Architecture）**の柱: 資源へのアクセスは**1つの資源・1回のセッションごと**に許可し、アイデンティティと状況（端末・場所・振る舞い）で**動的に判断**し、**最小権限**にし、すべての通信を**保護・記録**する。判断する部分（PDP: ポリシーエンジン＋管理者）と、通信の経路上で強制する部分（PEP）に分ける。
- **CISA Zero Trust Maturity Model 2.0**: 5つの柱（**ID／端末／ネットワーク／アプリケーション／データ**）と、共通の3つの力（**可視化と分析／自動化／ガバナンス**）を、4段階（従来型→初期→発展→最適）で見る。
- **OWASP セッション管理**: セッションには**無操作**と**絶対的な期限**の両方を設け、**サーバー側**で強制し、期限が切れたら**再認証**させる。

出典（検索で確認した解説。原文は NIST／CISA／OWASP の公式ページで確認してください）: [NIST SP 800-207 の解説（NordLayer）](https://nordlayer.com/learn/zero-trust/nist-sp-800-207/)、[Zero Trust Architecture の解説（Teleport）](https://goteleport.com/learn/zero-trust-architecture/)、[CISA ZTMM 2.0 の解説（Microsoft）](https://learn.microsoft.com/en-us/security/zero-trust/cisa-zero-trust-maturity-model-intro)、[OWASP Insufficient Session Expiration](https://owasp.org/index.php/OWASP_Periodic_Table_of_Vulnerabilities_-_Insufficient_Session_Expiration)。

## 診断（2026年10月時点）

| 見方 | もともとの状態 | 判定 | 今回の対応 |
|---|---|---|---|
| **IDを確かめる** | パスワード＋2段階認証（既定で必須）かパスキー。総当たり対策・ロック・新しい端末の通知 | ○ | 影響の大きい操作の前に**パスワードの入れ直し**（下記） |
| **リクエストごとに確かめる** | 各APIが毎回DBでセッション・ロック・役割を確認（役割はCookieでなくDB） | ○ | **ページとAPIのどちらも、入口（プロキシ）でも毎回確認**。以前は、ページはCookieの形だけ、サーバー側で終わったセッションのAPIは500だった |
| **端末を確かめる** | ブラウザ＋OSの固定、新しい端末の通知、PWAは端末の鍵（署名） | ○ | — |
| **ネットワークを信用しない** | セッションを接続元アドレスに固定、許可リスト・国の制限は任意 | ○（PWAは鍵で判断） | — |
| **最小権限** | 役割（管理者・経理・人事）と、メールボックスごと・部署ごとの権限。管理者もメールボックスに暗黙に入れない | △ | 下の「見つかった権限の穴」を修正 |
| **侵害を前提にする** | 監査ログ、セキュリティイベント、スイープ検知、自動ブロック | ○ | 権限変更・再確認の記録を追加 |
| **セッションの終わり** | 無操作10分・最長日数・サーバー側で強制 | △ | **終わったら必ずログイン画面へ**（下記） |
| **データへのアクセス（オブジェクト単位）** | 多くは確認済み。ただし一部に抜け | ✕→○ | 下記 |
| **端末の健全性（OSの更新・ウイルス対策）・振る舞いの採点** | なし | ✕ | 未対応（下の「残り」） |

結論: **「ゼロトラスト認証」の中心（毎回の確認・MFA・端末・最小権限・記録）はおおむね備わっていました。** ただし (1) 終わったセッションが画面に残る、(2) 影響の大きい操作に「いま本人か」の再確認がない、(3) 対象のモノに対する権限の確認が抜けたAPIがある、が弱点でした。今回、この3つを直しました。

## 今回の実装

### 1. セッションが終わったら、必ずログイン画面へ移る

- **終わる理由**: 無操作・他の端末からのログアウト・パスワード変更・アカウントのロック・接続元の変化・最長日数・管理者による終了。
- **入口で確認**（`src/proxy.ts` ＋ `src/lib/auth.ts` の `checkLive`）: Cookie の形が正しくても、サーバー側で終わったセッションなら、
  - **ページ**は、`/login?from=<元の画面>&reason=idle|expired` へ 307（元の画面と、理由つき。ログイン後に元の画面に戻る）。
  - **API**は、`401 {"error":"unauthorized"}`。（以前は、未ログインを 307 で返して、ブラウザがログイン画面のHTMLを「答え」として読んでいた。終わったセッションは、ルートが例外で落ちて 500 だった）
- **開いたままの画面**（`src/components/SessionGuard.tsx`）: 画面のどのAPI呼び出しが 401 を返しても、その場でログイン画面へ。一覧が空のまま・エラーのまま残らない。ホーム画面のアプリ（PWA）は、ログイン画面で端末の鍵で自動的に入り直す。
- **ログイン後の戻り先**（`src/lib/safe-redirect.ts`）: このアプリの中の画面だけ。**外のサイトへ飛ぶ細工（オープンリダイレクト）があったのを塞ぎました**（`/login?from=https://…` で、パスワードを入れた直後に別サイトへ移れた）。
- テスト: `e2e/session-end.spec.ts`（8つの画面を開く／開いたまま操作／アプリ内の移動／戻る先／外のサイトへ飛ばない／ロック／APIの返事）、`tests/unit/safe-redirect.test.ts`。

### 2. 影響の大きい操作は、パスワードを「いま」入れ直す（ステップアップ認証）

- 対象: ユーザーの追加・変更・削除、メールボックスの権限変更、セキュリティの条件・管理画面の設定の変更、MFAのリセット・アカウントのロック・全リセット、振込データの作成・ダウンロード、振込済の記録・CSV出力、取引先の口座の変更、全銀の設定、給与明細の登録・変更・削除、年末調整のCSV出力。
- 仕組み（`src/lib/reauth.ts`）: ログイン、または「パスワードの入れ直し」（`POST /api/auth/reauth`）から**設定の分数（既定15分）以内**でないと、`403 {"error":"recent_login_required"}`。**画面は、その場でパスワード（設定していれば認証コードも）を聞き**、確認できたら**同じ操作をそのまま実行**します（入力したものは消えません）。
- 盗まれたCookie、席を離れたままの画面、端末の鍵で自動的に入り直したアプリ（鍵は端末の証明で、本人の証明ではない）では、これらを実行できません。
- 間違いは15分に5回まで（超えると429）。記録（`reauth_success`／`reauth_failed`）。
- 設定: 管理画面「セキュリティ → アクセスの条件」の「重要な操作の前に…入れ直しを求める分数」（0=求めない）。e2e は `SECURITY_REAUTH_MINUTES=0` で動かし、`e2e/reauth.spec.ts` が有効にして確かめます。
- パスワードのないアカウント（パスキーだけ）は、入れ直しができないので、ログインし直した直後の分数以内だけ実行できます。

### 3. 見つかった権限の穴（オブジェクト単位）の修正

別の担当にすべてのAPIを読ませた確認（読むだけ）の結果のうち、確かめて直したものです。

| 重さ | 内容 | 修正 |
|---|---|---|
| 高 | `threads/bulk` の `ids` は、見られないスレッドにも効いた（他人の個人メールボックスの削除・迷惑メール指定・全体への送信元ブロック）。名指しで消すと、大量削除の承認も避けられた | 見られるスレッドだけに絞る。承認の確認は名指しでも行う |
| 高 | Mattermostへの共有（discuss）・連携（link）・転送（forward）は、スレッドを見られない人でも実行でき、件名・送信者・本文の冒頭が投稿され、リンクに好きなURLを入れられた | スレッドを見られる人だけ（それ以外は404）。リンクは会社のMattermostのURLだけ |
| 高 | 振込申請の承認は「承認したときの口座」と結び付いておらず、承認のあとに取引先の口座を書き換えて自分で確認済みにすれば、そこへ振り込めた | 承認のときの口座の指紋を残し、変わっていたら**CSV・振込済・全銀データのどれにも入れない**。管理者が新しい口座を確認し直す（`/api/payments/:id/reconfirm`）まで止まる |
| 中 | スレッドの移動: 管理者が他人の個人メールを移せた／行き先のチームを確認していなかった | 持ち主だけ。行き先は自分が入っているチームだけ |
| 中 | 下書き: 見られないメールボックス・スレッドを指定して作れた（そのチームの人に見える） | 返信できるメールボックス・見られるスレッドだけ |
| 中 | 担当の割り当て: そのメールを見られない人を担当にして、件名とリンクを送れた | 見られる人だけ |
| 中 | 連絡先のGoogle連携の戻り: `state` が本人のIDで、他人のGoogleアカウントを連携させる罠が成立した | ランダムな値をCookieで照合（カレンダーと同じ） |
| 中 | `/api/cron/*`: `CRON_SECRET` が未設定だと `Bearer undefined` で通った | 秘密が未設定・短い（16文字未満）なら、誰も通さない。固定時間の比較 |
| 中 | 管理画面の設定: 任意のキー・改行つきの値を `.env` に書けた | 管理している項目だけ。改行・長すぎる値は400 |
| 中 | 自分についての金額: 経理・管理者が自分の給与明細・年末調整の確認・自分の出張の手当を、自分で登録・確認できた | ほかに経理担当・管理者がいる間は、自分の分は作れない・直せない・確認できない（`self_dealing`） |
| 中 | 人事が、自分を経費の承認者に指定できた | 管理者だけが、自分を指定できる |
| — | メールボックス権限の変更が、記録に残らなかった | 監査ログ（`mailbox_permissions_update`）。パスワードの入れ直しも必要 |

テスト: `e2e/zero-trust.spec.ts`（13件）、`e2e/payment-account-binding.spec.ts`、`tests/unit/cron-auth.test.ts`。

## 残り（今回は未対応）

- **二重払いの経路**: `transfers/batches` の `force`（すでに別のファイルに入った明細を、もう一度入れる）と、個別の「振込済」と全銀データの重複（`batch_id` を見ていない）。
- **ほかの金額の確認**: 勤怠の経理による自分の修正、オートフローの自分の分、出張の手当マスタ。
- **メール**: 迷惑メール指定・送信者の許可が、閲覧だけの人にも可能（全体のリスト）。単発の削除は、一括削除の承認の確認を通らない。予約送信は、送信の時点で権限を確認し直さない。
- **連絡先**は、全員で共有する1冊で、持ち主がない（編集・削除は誰でも）。Googleの連絡先の同期は、他人の行を上書きし得る。
- **管理者の力**: ほかのユーザーのメール・パスワード・MFAを変えられる（今回、入れ直しを必須にし、記録はある。変更を本人に通知する仕組みはなし）。
- **端末の健全性**（OSの更新・画面ロック・ウイルス対策）の確認、リスクの採点（普段と違う場所・時間・量）、DBSC（ブラウザが鍵でセッションを縛る仕組み。仕様を確認できなかったため見送り）。
- **ユーザー一覧**（`/api/users`）は、全員のメール・役割を全員に返す。
- 経費・出張の承認は、承認者が読んだ内容と承認の瞬間の内容が同じかを確かめない（承認時の版を固定していない）。
