# 管理画面（システム管理者専用）

メニューの「管理」は、**1か所にまとまった管理画面**です。上のバーで画面を選びます。システム管理者だけが入れます（ほかの人は `proxy.ts` がトップへ戻し、`/api/admin/*` はどれも403を返します）。

| 画面 | URL | 内容 |
|---|---|---|
| システム設定 | `/admin/settings` | メール同期・通知・Google連携・アイコンなど、アプリ全体の設定 |
| ユーザー | `/admin/users` | アカウントの追加・変更・削除 |
| メールアカウント | `/admin/mailboxes` | 個人・チームのメールと、見られる人の権限 |
| 迷惑メール | `/admin/spam` | 拒否・許可するアドレス、自動判定の学習データ |
| セキュリティ | `/admin/security` | 下の4項目 |
| 運用ログ | `/admin/operations` | メール接続のエラー、通知の失敗、監査ログ |

- 以前は「管理」と「セキュリティ」が別のメニューで、巨大な1画面（`/admin/settings`）に全部が入っていました。画面ごとのファイルに分け（`src/components/admin/AdminSettings.tsx` が `tab` で出し分け）、**開いた画面に必要なデータだけ**を読みます。
- メニューの別項目だった「セキュリティ」はなくなり、管理の中の画面になりました。個人のパスワード・パスキー・2段階認証・自分のログイン履歴は、これまでどおり**プロフィール**にあります（本人が自分で管理するため）。

## セキュリティの4項目（`#overview` `#accounts` `#history` `#access`）

| 項目 | 内容 | 読むAPI |
|---|---|---|
| 概要 | 24時間の失敗・成功、失敗が多いアドレスと狙われたアカウント、ブロック中のアドレス、検知したできごと | `GET /api/admin/security/overview?lite=1` |
| アカウントと端末 | ロック中のアカウント、ログイン方法（2段階認証・パスキー）、**ログイン中の端末**（遮断できる） | `GET /api/admin/security/people`・`GET /api/admin/sessions` |
| ログイン履歴 | 検索（メール・IP・組織・場所）、「失敗だけ」、50件ずつ「もっと見る」 | `GET /api/admin/login-logs?q=&failed=1&before=` |
| アクセスの条件 | 許可ネットワーク・国、2段階認証、ロボット遮断、アプリのログイン維持、セッションの最長日数 | `GET/PUT /api/admin/security/policy` |

選んだ項目だけが画面に出るので、その項目のデータだけを取りに行きます。`/admin/security#access` のようにリンクで直接開けます。

## 経理担当・人事担当

管理者は、勤怠・給与の「管理 › 区分・設定」で人に「経理担当」「人事担当」の印を付けられます。範囲は [23_org_and_evaluations.md](23_org_and_evaluations.md) を参照してください。

## DBの取りに行き方を軽くした点

同じデータ（ログイン履歴3000件・監査ログ800件など）で、変更前（`3ceb2ed`）と変更後を、画面ごとの **SQLの本数** で比べました（`PRISMA_LOG_QUERIES=1` で出したSQLを `scripts/measure-queries.mjs` で数えた値。開発サーバー、設定のキャッシュは本番と同じ既定の時間）。

| 画面 | 変更前（API / SQL） | 変更後（API / SQL） |
|---|---|---|
| システム設定 | 3 / 9 | 2 / 4 |
| ユーザー | 3 / 9 | 1 / 2 |
| メールアカウント | 4 / 15 | 2 / 4 |
| 迷惑メール | 5 / 18 | 2 / 4 |
| セキュリティ（概要） | 2 / 16（全部入り） | 1 / 8 |
| ログイン履歴 | 5 / 17（旧タブ） | 1 / 2 |
| 運用ログ | 3 / 12 | 3 / 6 |
| 認証の確認だけ（全APIに共通） | 1 / 2 | 1 / 1 |

やったこと:

1. **タブごとに必要なものだけ読む。** 以前は、どのタブを開いても「設定・ユーザー一覧・Google連携」を毎回読んでいました。
2. **関連データを1本のSQLで読む（`relationJoins`）。** Prisma の `relationLoadStrategy: 'join'` を既定にし（`schema.prisma` の `previewFeatures`）、「本体＋関連」を1回で読みます。全リクエストに共通のセッション確認は2本→1本になりました（アプリ全体に効きます）。
3. **集計はDBにやらせる。** 概要の「失敗が多いアドレス／アカウント」は、失敗ログを最大5000行読んでアプリ側で数える方式をやめ、`GROUP BY` の集計（上位8件）に。24時間の成功・失敗の件数も1本の集計です。パスキーの数も、1人ずつ数えずに一括で集計します。そのための索引 `login_logs(success, created_at)` を追加。
4. **一覧は必要な列だけ・ページ送り。** ログイン履歴は新しい順に50件ずつ（`before` で続き）。セッション一覧は最大300件、通知の失敗は必要な列だけ。
5. **余計な問い合わせを減らす。** 管理者かどうかの確認に使っていた追加のDB読み込み（役割だけを読むためのもの）をやめ、セッションの確認で得た役割を使います。設定の保存は、1件ずつ順に書くのをやめ、1回のまとまった書き込み（トランザクション）にしました。

> 数え方の注意: 数値は開発サーバーでの実測で、バックグラウンドの処理（メール同期など）のSQLが混ざらないよう、各画面を複数回流して最小値を取っています。本番でも、画面ごとの差はほぼ同じ比率で出ます。時間（ミリ秒）は環境で変わるので、SQLの本数を主な指標にしています。

## 安全のための修正（同じときに直したもの）

管理用のAPIのいくつかが、**ルートの中で管理者かどうかを確認していませんでした**（設定の取得・保存、VAPID鍵の生成、監査ログ、接続エラー、通知エラーとその再送、ユーザーの作成）。`proxy.ts` が管理者だけを通していましたが、プロキシが見るのはCookieに入った役割で、**管理者から外された人の古いCookieでは通ってしまいます**。ユーザー作成は、ログインしていれば誰でも管理者を作れる状態でもありました。

- すべての `/api/admin/*` で、**DBの今の役割**を見て断ります（`adminActor()`）。
- `POST /api/admin/users` は管理者だけ。作るのは一般ユーザーが既定（最初の1人だけが管理者）。
- 「管理者から外された人が古いCookieで入れない」ことは `e2e/admin-console.spec.ts` で確かめています。

## 測り方

```bash
PRISMA_LOG_QUERIES=1 npm run dev:nodb > /tmp/server.log 2>&1 &       # SQLを標準出力へ
node scripts/measure-queries.mjs http://localhost:3000 /tmp/server.log scenarios.json  # 画面ごとのSQL本数
```
`scenarios.json` は `[{ "name": "ユーザー", "requests": [["GET", "/api/users"]] }, ...]`。
