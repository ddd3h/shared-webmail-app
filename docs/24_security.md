# セキュリティ（ログイン・アクセス元・スイーピング対策）

## 全体像

```
リクエスト ─▶ ① 接続元の判定 ─▶ ② ブロック/許可ネットワーク ─▶ ③ 他サイトからの更新を拒否（Origin）
          ─▶ ④ ログインなしの探索を検知 ─▶ ⑤ ログイン済みの利用上限 ─▶ 各API（権限チェック）
```
①〜⑤は `src/proxy.ts`、ログインは `/api/auth/login`（`src/lib/login-guard.ts`）、ログイン後の処理は `src/lib/login-flow.ts`。

## 1. 接続元（どこからアクセスしているか）

- **正しいIPの決め方**（`src/lib/client-ip.ts`）: `X-Forwarded-For` の左端はクライアントが好きな値を書けるため、IP単位の制限をすべて回避できてしまいます。自社のプロキシ（nginx）が**追記した右側**を使います。プロキシの台数は `TRUSTED_PROXY_COUNT`（既定 1）。0 ならヘッダーを信用しません。
  - nginx は `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;` にしてください（`scripts/setup.sh` と `deploy/nginx-collab.conf` はそうなっています）。
- **ログインの履歴**: 成功・失敗ごとに、時刻・IP・端末（ブラウザとOS）・国と市区町村・ネットワークの種類（自宅／公共Wi-Fi／クラウド・VPN）を記録します。
  - 本人は **プロフィール →「最近のログイン履歴」** で自分の分を見られます。管理者は `/admin/security` で全体を見られます。
- **ログイン中の端末**: プロフィールで、いま使われている端末（端末名・場所・IP・最後の操作）を確認し、**1台ずつ終了**、または**他をすべてログアウト**できます。同時にログインできるのは10台までで、超えると使っていない端末から終了します。
- **新しい端末の通知**: その人が使ったことのないブラウザ（Cookie `did` の有無で判定）からログインすると、**本人にMattermostで通知**します（日時・端末・場所・方法）。最初の1台は通知しません。設定でオフにできます。
- **アクセス元の制限**（管理者・`/admin/security` →「アクセスの条件」）:
  - **使えるネットワーク**（IP または `203.0.113.0/24`）: 設定すると、それ以外のアドレスからは**ログインも利用もできません**（既存のセッションも止まります）。**自分のアドレスが含まれない設定は保存できません**（自分を締め出さないため）。
  - **ログインを許可する国**（例 `Japan`）: ログイン時のIP照会の国で判定します。許可外の国からは、パスワードが合っていても**同じ401**を返し、合っていることを教えません。
  - **ブロック**: アドレスや範囲を手動でブロック（期限つきも可）。自分のアドレスはブロックできません。

## 2. ログインへの攻撃（総当たり・クレデンシャルスタッフィング・スイーピング）

| 対策 | 内容 |
|---|---|
| 同じ答え | パスワード違い・存在しないアカウント・ロック中・許可外の国は**すべて同じ401**。存在しないアカウントでも同じ重さのパスワード検証をして、**応答時間でも見分けられない** |
| 重ねた制限 | ①1アドレス20回/15分 ②**同じアカウント×同じアドレス5回/15分**（打ち間違いはそのアドレスだけ止まる）③同じアカウント全体15回/15分 ④DBの失敗記録40回/15分（**再起動しても続く**） |
| 他人に締め出されない | ③④は「**このアカウントで以前ログインしたことのある端末のCookie**」を持つ人には適用しません。攻撃者がアカウントを狙って失敗を重ねても、本人の端末は入れます |
| スイーピング検知 | **1つのアドレスが10分間に9個以上の別アカウント**を試すと、自動で60分ブロックしてアラート |
| 自動ブロック | 制限に何度も当たるアドレス（1時間に3回）は、60分ブロック。ループバック（このマシン自身）は対象外 |
| 本人への通知 | アカウントが制限されたとき、本人に「ログインに繰り返し失敗しています」とMattermostで通知。管理者にはメール（既存のDoSアラート） |
| 入力検証 | 本文が壊れている・文字列でない・1000文字超は400（重い処理をさせない）。メールアドレスは前後の空白・大文字小文字を無視 |
| パスキー | ブロック・許可ネットワーク・回数制限・ロック・許可国を同じように適用。本番では**自分のURL以外のOrigin**ではパスキー認証を受け付けない（トンネル用に `PASSKEY_ALLOW_ANY_ORIGIN=1`） |

## 3. 利用中の探索（スイーピング）

`src/lib/sweep-guard.ts`・`src/lib/api-budget.ts`

- **ログインしないまま**多数の別パスを探る（5分に16種類以上。`/wp-admin`・`/.env`・APIの総当たりなど）、またはAPIを毎分30回超 → 429、スキャンは**アドレスを60分ブロック**。
- **ログイン済み**でも、重要なAPIには1分あたりの上限があります。通常の利用では届きません。
  | 種類 | 上限/分 |
  |---|---|
  | 支払CSV出力 | 10 |
  | 受取口座 / 全銀設定 | 60 |
  | 全銀データ | 120 |
  | 請求書・領収書のダウンロード | 120 |
  | 管理API | 300 |
  | その他のAPI | 900 |
- **他人のレコードのURLを次々に読む**（1分に80件以上の別ID）と、スイーピングとして止めて、記録し、アドレスにストライクを付けます。
- 接続元が分からないリクエストは、アドレス単位の判定をしません（全員を同じ扱いにして巻き込まないため）。
- 特定のユーザー（バッチ処理など）を上限から外す: `API_BUDGET_EXEMPT_USER_IDS=u1,u2`

## 4. セッション・Cookie

- **別の種類の端末でのCookie使い回しを拒否**: セッションはログイン時のブラウザ＋OS（バージョンは無視）に結び付き、別の種類の端末から使うと**そのセッションを終了**して記録します（`session_device_mismatch`）。管理者がオフにできます。
- **最長寿命**: 操作を続けていても、設定した日数（既定14日）でログアウトします。
- **役割はDBから**: Cookieの役割は信用せず、毎回DBの役割とロック状態を見ます。降格・ロックが**すぐに**効きます。
- **ロック**: 管理者が `/admin/security` からアカウントをロックでき、全端末がログアウトされ、ログインできなくなります（自分自身・最後の管理者はロック不可）。
- **パスワード**: 10文字以上、よくある語・メール・名前を含むものは不可（`src/lib/password-policy.ts`）。**変更すると他の端末がログアウト**、管理者が設定・リセットした場合は全端末がログアウト。変更時は現在のパスワードを再確認し、試行は5回/15分。
- **Cookieの鍵**: 本番で `SESSION_SECRET` が未設定・開発用の値・32文字未満だと、**セッションを発行せず、ログインをエラー**にします（ログに理由が出ます）（誰でもCookieを偽造できてしまうため）。
- Cookie は HttpOnly・SameSite=Lax・本番では Secure。ログインのたびに新しいセッションIDになります（セッション固定の対策）。

## 5. 他サイトからの攻撃・ブラウザの防御

- **CSRF**: 更新リクエスト（POST/PUT/PATCH/DELETE）の `Origin` が自分のサイトでなければ403。`Origin: null` も拒否し、記録します。
- ヘッダー: CSP・HSTS・`X-Frame-Options: DENY`・`nosniff`・`Referrer-Policy`・`Permissions-Policy`・**COOP/CORP（same-origin）**。個人情報を含むAPI（認証・口座・振込・管理・プロフィール）は `Cache-Control: no-store`。

## 6. 管理者の画面（`/admin/security`）

直近24時間の失敗・成功・ログイン中のセッション数、失敗が多いアドレス／狙われているアカウント、**検知したできごと**（スイーピング・自動ブロック・Cookie使い回し・他サイトからの更新など）、ブロック中のアドレス（解除可）、ロック中のアカウント、アクセスの条件、最近のログイン。すべての操作は監査ログに残ります。

## 7. 2段階認証（パスキー、または パスワード＋2段階認証）

ログインできるのは次のどちらかだけです（管理者がルールを有効にしている間。**既定は有効**）。

| 方法 | 内容 |
|---|---|
| パスキー | 端末の生体認証・PINなど。これだけで完結（2段階認証は不要） |
| パスワード ＋ 2段階認証 | パスワードのあとに、認証アプリの6桁コード（または回復コード）を入力 |

パスワードだけではセッションは作られません（パスワード後〜コード入力までは、5分で切れる署名付きの「引換券」だけが存在します）。

### 流れ
1. **まだ設定していない人**: パスワードの後、そのままログイン画面の中でQRコードを読み取って設定 → 6桁コードで確認 → **回復コード10個**を表示（これを保存して初めてログイン完了）。
2. **設定済みの人**: パスワードの後に6桁コード。「このブラウザを信頼する」にチェックすると、期間中（既定30日）はコードを省略できます。
3. **コードを紛失**: 回復コード（`xxxxx-xxxxx`）を1回だけ使えます。使うと管理者・本人へ通知。回復コードでのログインでは「信頼」は付与されません。

### 守っていること
- TOTP（RFC 6238 / SHA-1 / 6桁 / 30秒、前後1ステップまで許容）。同じコードの**再利用は不可**（使用済みステップを記録）。
- 秘密鍵は暗号化して保存。回復コードは `SESSION_SECRET` で鍵付きハッシュ化して保存し、**同時に2回使っても1回しか成功しません**。
- コード入力は、アカウントごと（15分に5回）・接続元ごと（15分に20回）で制限。超えるとロックの記録と通知が残ります。
- 次の操作で、信頼したブラウザはすべて無効になります: パスワード変更・リセット、アカウントのロック、他の端末のログアウト、2段階認証の解除／リセット。
- 設定の変更（無効化・回復コードの再発行）には、パスワード（と現在のコード）での再確認が必要です。

### 画面
- ユーザー: プロフィール →「2段階認証」（設定／回復コードの再発行／解除）。
- 管理者: `/admin/security` →「ログイン方法」で全員の設定状況（2段階認証・パスキー）を一覧。**リセット**（紛失時。セッションも終了し、次回ログイン時に再設定）。ルールのオン／オフと信頼期間（0日で無効）は「アクセスの条件」から。ルールを切ると警告のできごとが記録されます。

### 導入時の注意
ルールを有効にすると、パスキーを持たない既存ユーザーは**次のパスワードログインで2段階認証の設定を求められます**。

## 環境変数

| 変数 | 意味 |
|---|---|
| `TRUSTED_PROXY_COUNT` | 手前にあるプロキシの台数（既定 1）。0 で `X-Forwarded-For` を信用しない |
| `SESSION_SECRET` | 32文字以上のランダム文字列。本番では必須 |
| `PASSKEY_ALLOW_ANY_ORIGIN` | `1` で、本番でも任意のOriginでパスキーを許可（ngrok等。通常は設定しない） |
| `API_BUDGET_EXEMPT_USER_IDS` | 利用上限の対象外にするユーザーID（カンマ区切り） |
| `SECURITY_REQUIRE_2FA` | 設定キー（画面から変更）。`off` で2段階認証ルールを無効化。E2Eは既定で `off` |
| `SECURITY_CACHE_TTL_MS` | 設定・ブロック一覧をメモリに覚える時間（既定 10〜15秒） |

## 限界（知っておいてください）

- ログインの回数・探索の判定は**メモリ上**です（1台構成が前提）。再起動すると数分の記録は消えます（ログインの失敗回数はDBでも数えるので、そちらは残ります）。複数台にするなら Redis などへの移行が必要です。
- IPの国・ネットワークの判定は外部サービス（ip-api.com）に頼っています。失敗したときは「許可」側に倒れます（利用を止めないため）。
- 端末の識別はCookieです。Cookieを消すと「新しい端末」になります。
