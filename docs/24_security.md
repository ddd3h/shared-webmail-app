# セキュリティ（ログイン・アクセス元・スイーピング対策）

## 全体像

```
リクエスト ─▶ ① 接続元の判定 ─▶ ② ブロック/許可ネットワーク ─▶ ③ 他サイトからの更新を拒否（Origin）
          ─▶ ④ ログインなしの探索を検知 ─▶ ⑤ ログイン済みの利用上限 ─▶ 各API（権限チェック）
```
①〜⑤は `src/proxy.ts`、ログインは `/api/auth/login`（`src/lib/login-guard.ts`）、ログイン後の処理は `src/lib/login-flow.ts`。

## 1. 接続元（どこからアクセスしているか）

- **正しいIPの決め方**（`src/lib/client-ip.ts`）: `X-Forwarded-For` の左端はクライアントが好きな値を書けるため、IP単位の制限をすべて回避できてしまいます。自社のプロキシ（nginx）が**追記した右側**を使います。プロキシの台数は `TRUSTED_PROXY_COUNT`（既定 1）。0 ならヘッダーを信用しません。
- **Cloudflare を使うとき**: つなぎ方で設定が変わります。
  | つなぎ方 | 設定 |
  |---|---|
  | ブラウザ → Cloudflare → **アプリ**（nginx なし）、または Cloudflare Tunnel（cloudflared） | `TRUSTED_PROXY_COUNT=1`（既定のまま）で正しく動きます |
  | ブラウザ → Cloudflare → **nginx** → アプリ | 既定の nginx 設定（`$proxy_add_x_forwarded_for`）のままだと、アプリが受け取る接続元の末尾が**Cloudflare のアドレス**になり、IP固定のセッションがランダムに切れ、IP単位の制限やブロックが全員に及びます。`deploy/nginx-cloudflare.conf` の設定（Cloudflare の範囲からだけ `CF-Connecting-IP` を信用し、アドレスを1つだけ渡す）にして、`TRUSTED_PROXY_COUNT=1` のままにしてください。範囲の一覧は `deploy/update-cloudflare-ips.sh` で更新します |
  Cloudflare 側は、**Email Address Obfuscation（メールアドレスの難読化）・Rocket Loader・Auto Minify をオフ**にしてください（画面の書き換えで表示が崩れます）。`/api/cron/*` にはボット対策（Bot Fight Mode・チャレンジ）を適用しないルールを入れてください。アップロードの上限は Cloudflare の無料・Pro プランで100MBです（アプリは1通10ファイル×10MB＋余白で、超えると 413 になります）。nginx は Cloudflare のアドレスからだけ受け付けるように、ファイアウォールで閉じてください。
- **IPアドレスが分からないリクエストは拒否**（403 `ip_unknown`）: プロキシの設定ミス（`TRUSTED_PROXY_COUNT` の誤り、プロキシを通っていない、`X-Forwarded-For` が不正な値）でアドレスが取れないと、制限・ブロック・セッションのIP確認がすべて効かなくなるため、通しません。「検知したできごと」に記録します（1分に1回まで）。スケジューラ用の `/api/cron/*` は秘密キーで守られているので対象外です。**`TRUSTED_PROXY_COUNT=0` はアドレスが常に不明になるため、全員が入れなくなります。通常は設定しないでください。**
  - nginx は `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;` にしてください（`scripts/setup.sh` と `deploy/nginx-collab.conf` はそうなっています）。
- **ログインの履歴**: 成功・失敗ごとに、時刻・IP・端末（ブラウザとOS）・国と市区町村・ネットワークの種類（自宅／公共Wi-Fi／クラウド・VPN）を記録します。
  - 本人は **プロフィール →「最近のログイン履歴」** で自分の分を見られます。管理者は `/admin/security` で全体を見られます。
- **ログイン中の端末**: プロフィールで、いま使われている端末（端末名・場所・IP・最後の操作）を確認し、**1台ずつ終了**、または**他をすべてログアウト**できます。同時にログインできるのは10台までで、超えると使っていない端末から終了します。
- **新しい端末の通知**: その人が使ったことのないブラウザ（Cookie `did` の有無で判定）からログインすると、**本人にMattermostで通知**します（日時・端末・場所・方法）。最初の1台は通知しません。設定でオフにできます。
- **アクセス元の制限**（管理者・`/admin/security` →「アクセスの条件」）:
  - **使えるネットワーク**（IP または `203.0.113.0/24`）: 設定すると、それ以外のアドレスからは**ログインも利用もできません**（既存のセッションも止まります）。**自分のアドレスが含まれない設定は保存できません**（自分を締め出さないため）。
  - **ログインを許可する国**（例 `Japan`）: ログイン時のIP照会の国で判定します。許可外の国からは、パスワードが合っていても**同じ401**を返し、合っていることを教えません。
  - **ブロック**: アドレスや範囲を手動でブロック（期限つきも可）。自分のアドレスはブロックできません。

## 2. ログインへの攻撃（総当たり・クレデンシャルスタッフィング・スイーピング）

| 対策 | 内容 |
|---|---|
| 同じ答え | パスワード違い・存在しないアカウント・ロック中・許可外の国は**すべて同じ401**。存在しないアカウントでも同じ重さのパスワード検証をして、**応答時間でも見分けられない** |
| 重ねた制限 | ①1アドレス20回/15分 ②**同じアカウント×同じアドレス5回/15分**（打ち間違いはそのアドレスだけ止まる）③同じアカウント全体15回/15分 ④DBの失敗記録40回/15分（**再起動しても続く**） |
| 他人に締め出されない | ③④は「**このアカウントで以前ログインしたことのある端末のCookie**」を持つ人には適用しません。攻撃者がアカウントを狙って失敗を重ねても、本人の端末は入れます |
| スイーピング検知 | **1つのアドレスが10分間に9個以上の別アカウント**を試すと、自動で60分ブロックしてアラート |
| 自動ブロック | 制限に何度も当たるアドレス（1時間に3回）は、60分ブロック。ループバック（このマシン自身）は対象外 |
| 本人への通知 | アカウントが制限されたとき、本人に「ログインに繰り返し失敗しています」とMattermostで通知。管理者にはメール（既存のDoSアラート） |
| 入力検証 | 本文が壊れている・文字列でない・1000文字超は400（重い処理をさせない）。メールアドレスは前後の空白・大文字小文字を無視 |
| パスキー | ブロック・許可ネットワーク・回数制限・ロック・許可国を同じように適用。本番では**自分のURL以外のOrigin**ではパスキー認証を受け付けない（トンネル用に `PASSKEY_ALLOW_ANY_ORIGIN=1`） |

## 3. 利用中の探索（スイーピング）

`src/lib/sweep-guard.ts`・`src/lib/api-budget.ts`

- **ログインしないまま**多数の別パスを探る（5分に16種類以上。`/wp-admin`・`/.env`・APIの総当たりなど）、またはAPIを毎分30回超 → 429、スキャンは**アドレスを60分ブロック**。
- **ログイン済み**でも、重要なAPIには1分あたりの上限があります。通常の利用では届きません。
  | 種類 | 上限/分 |
  |---|---|
  | 支払CSV出力 | 10 |
  | 受取口座 / 全銀設定 | 60 |
  | 全銀データ | 120 |
  | 請求書・領収書のダウンロード | 120 |
  | 管理API | 300 |
  | その他のAPI | 900 |
- **他人のレコードのURLを次々に読む**（1分に80件以上の別ID）と、スイーピングとして止めて、記録し、アドレスにストライクを付けます。
- 接続元が分からないリクエストは、アドレス単位の判定をしません（全員を同じ扱いにして巻き込まないため）。
- 特定のユーザー（バッチ処理など）を上限から外す: `API_BUDGET_EXEMPT_USER_IDS=u1,u2`

## 4. セッション・Cookie

- **ログインしたIPアドレスでしか使えない**: セッションはログインしたときのIPアドレスに結び付き、**別のIPアドレスから使われると、そのセッションを終了**します（Cookieも削除。`session_ip_mismatch` を記録）。盗まれたCookieを別の場所から使われても、持ち主の端末も含めて即座に無効になり、持ち主は再ログインします。リクエストごとに `src/proxy.ts`（Cookie内のIP）と `getSession()`（DBのIP）の両方で確認します。
  - IPv6は、同じ回線（先頭64ビット）の中で下位が変わる（プライバシー拡張）だけなら同じ扱いです。IPv4は完全一致、このマシン自身（`::1`/`127.0.0.1`）は同じ扱いです。
  - 副作用: スマホがWi-FiとモバイルLTE/5Gを切り替える、VPNを切り替える、など**IPが変わると再ログインが必要**です（常に有効で、オフにする設定はありません）。
- **別の種類の端末でのCookie使い回しを拒否**: セッションはログイン時のブラウザ＋OS（バージョンは無視）に結び付き、別の種類の端末から使うと**そのセッションを終了**して記録します（`session_device_mismatch`）。管理者がオフにできます。
- **最長寿命**: 操作を続けていても、設定した日数（既定14日）でログアウトします。
- **役割はDBから**: Cookieの役割は信用せず、毎回DBの役割とロック状態を見ます。降格・ロックが**すぐに**効きます。
- **ロック**: 管理者が `/admin/security` からアカウントをロックでき、全端末がログアウトされ、ログインできなくなります（自分自身・最後の管理者はロック不可）。
- **パスワード**: 10文字以上、よくある語・メール・名前を含むものは不可（`src/lib/password-policy.ts`）。**変更すると他の端末がログアウト**、管理者が設定・リセットした場合は全端末がログアウト。変更時は現在のパスワードを再確認し、試行は5回/15分。
- **Cookieの鍵**: 本番で `SESSION_SECRET` が未設定・開発用の値・32文字未満だと、**セッションを発行せず、ログインをエラー**にします（ログに理由が出ます）（誰でもCookieを偽造できてしまうため）。
- Cookie は HttpOnly・SameSite=Lax・本番では Secure。ログインのたびに新しいセッションIDになります（セッション固定の対策）。

## 5. 他サイトからの攻撃・ブラウザの防御

- **CSRF**: 更新リクエスト（POST/PUT/PATCH/DELETE）の `Origin` が自分のサイトでなければ403。`Origin: null` も拒否し、記録します。
- ヘッダー: CSP・HSTS・`X-Frame-Options: DENY`・`nosniff`・`Referrer-Policy`・`Permissions-Policy`・**COOP/CORP（same-origin）**。個人情報を含むAPI（認証・口座・振込・管理・プロフィール）は `Cache-Control: no-store`。

### ロボット（AI・クローラ・スクリプト）の遮断

`src/proxy.ts` の `botRules`（判定は `src/lib/bot-guard.ts`）。すべてのリクエストの User-Agent を見て、次のものは**403（`bots_not_allowed`）**で断ります。ログイン画面もAPIも、ログイン済みのCookieを持っていても対象です。

| 種類 | 例 |
|---|---|
| AI・データ収集のクローラ | GPTBot・ChatGPT-User・OAI-SearchBot・ClaudeBot・Claude-Web・anthropic-ai・PerplexityBot・CCBot・Google-Extended・Bytespider・Amazonbot・Applebot・Meta-ExternalAgent・cohere-ai・Diffbot・SemrushBot・AhrefsBot など |
| スクリプト・自動ツール | curl・wget・python-requests・Go-http-client・okhttp・axios・node-fetch・Postman・Googlebot などの `bot/` や `+http://…` を名乗るもの |
| 自動操作ブラウザ | HeadlessChrome・PhantomJS・Puppeteer・Playwright・Selenium・Lighthouse |
| User-Agent が無い接続 | （空） |

- **管理画面の「アクセスの条件」でオン／オフ**できます（既定はオン・推奨）。環境変数 `BOT_BLOCK=off` で、画面の設定に関わらず全体を止められます。
- 例外（監視ツールなど）は `BOT_ALLOW_UA="UptimeRobot,..."`（User-Agent に含まれる文字。カンマ区切り）。
- **`/api/cron/`（定期処理）は対象外**です（スクリプトから、鍵つきで呼ぶため）。`/robots.txt` はロボットにも見せます（403だと「何も禁止されていない」と読む実装があるため）。
- 断ったことは「セキュリティイベント」に `bot_blocked` として残ります（同じアドレス・同じ種類は1分に1回）。アドレスの自動ブロックまではしません（共有のNATで巻き込む恐れがあるため）。
- お願いの仕組みも併用: `public/robots.txt`（全ロボットに全面禁止）、全ページの `X-Robots-Tag: noindex, nofollow, noarchive, nosnippet, noimageai, noai`、`<meta name="robots">`。
- **限界**: これは**名乗る相手にしか効きません**。User-Agent を偽装するスクリプトや、普通のChromeを自動操作するものは、この遮断だけでは止まりません。そちらは、これまでの仕組み（ログインした接続元のアドレスにセッションを固定・パスワード＋2段階認証・リクエストの上限・探索（スイーピング）の検知）で守ります。

### アプリ（PWA）は端末の鍵だけで判断する

「ログインを維持する」を選んだホーム画面のアプリ（鍵で入り直したセッション、またはその設定でパスワードログインしたセッション。セッションに `pwa` の印が付く）は、**端末の鍵が本人の証明のすべて**で、次の制約は掛けません。VPN（Cloudflare WARP など）やWi-Fi／モバイル回線の切り替えで、アドレスが変わっても使い続けられます。

| 通常のブラウザ | ホーム画面のアプリ |
|---|---|
| 接続元のアドレスが変わるとセッションを破棄（`session_ip_mismatch`） | 破棄しない（`src/proxy.ts`・`getSession()`） |
| 無操作の自動ログアウト（既定10分） | しない（サーバーも画面も） |
| ブラウザ＋OSの種類が変わるとセッションを破棄（端末の固定） | 見ない |
| 入り直しのチャレンジは、もらったアドレスからだけ使える | アドレスは問わない（2分・1回限りは変わらない） |
| 入り直しは、ブラウザ＋OSの種類が登録時と同じことが条件 | 見ない（OSの更新で入れなくならない） |

- **残る確認**: `did` クッキー、署名（登録した公開鍵）、チャレンジの期限と1回限り、アカウントのロック、維持の日数、セッションの最長日数、そして管理画面の「許可する国」「許可するネットワーク」・アドレスのブロック・回数の制限（これらはアプリにも掛かります）。
- **引き換えに弱くなること**: アプリのセッションのCookie（`sid`）を盗まれた場合、盗んだ側が別のアドレス・別のブラウザから、最長日数の間使えます（通常のブラウザでは、アドレスが違えばその場で破棄されます）。紛失・盗難のときは「他の端末をログアウト」かアカウントのロックで止めます。
- 通常のブラウザの制約は、これまでどおりです。

### アプリ（PWA）のログイン維持（端末の鍵）

ホーム画面に追加したアプリは、**最後に使ってから30日間**（管理画面の「アクセスの条件」で変更。0で無効）、パスワードなしでログインし直せます。**30日間、一度も使わなければ、ログアウト**（次はパスワードが必要）です。使うたびに期限は延びます。

**なぜ端末の鍵か（localStorage に合言葉を置かない理由）**: localStorage は、ページ上のどのスクリプトからも読めます（XSS があれば盗まれます）。そこで、**端末ごとに作る鍵**で本人の端末かを確かめます。

- アプリは、ログインのときに **ECDSA P-256 の鍵のペア**をブラウザの WebCrypto で作ります。**秘密鍵は「取り出せない鍵」**として IndexedDB に置かれ、アプリ自身のスクリプトでも読めません（署名を頼めるだけ）。
- 公開鍵だけをサーバーに渡し、その **sha256 を「端末の個体番号」**（`known_devices.key_id`）として記録します。ブラウザやOSのシリアル番号（IMEI など）は、Web からは読めないので、この個体番号が「その1台のアプリ」を表します。
- セッションが切れたとき（無操作・別のネットワークに移った・日数）、アプリは `POST /api/auth/resume/challenge` で一度限りのチャレンジをもらい、**秘密鍵で署名して** `POST /api/auth/resume` に渡します。サーバーは次の**すべて**を確かめます。
  1. `did` クッキー（HttpOnly。この端末のブラウザの印）が、維持中の端末のもの
  2. **署名が、登録した公開鍵で正しい**（チャレンジは2分・1回限り）
  3. アカウントがロックされていない・許可された国・許可されたネットワーク（ブラウザ＋OSの種類とアドレスは見ない）
- アプリのセッションはアドレスで縛りません（上の表）。アプリを開いたまま前面に戻ったとき、`SessionKeeper` がセッションの有無を確認し、切れていれば入り直して再読み込みします。
- **盗まれても**: `did` クッキーだけ、個体番号だけでは入れません（署名が必要）。鍵は端末の外に出せません。拒否は「アプリの自動ログイン（端末の鍵）を拒否」として記録します（理由つき）。失敗が続くアドレスは、これまでの仕組みで自動ブロックされます。
- **鍵で入り直したセッションは、「入れる人」を変える操作ができません**: パスキーの登録・削除、受取口座の変更は「パスワードまたはパスキーでログインし直してください」（403 `reauth_required`）。パスワード変更・2段階認証の変更は、元々パスワードを聞くので同じです。
- **維持が終わるとき**: ログアウト、「他の端末をログアウト」、パスワード変更、2段階認証の変更・リセット、管理者がアカウントをロック、日数切れ、管理画面で日数を0に。
- 画面に出るのは**ホーム画面のアプリ（standalone）だけ**です。通常のブラウザには、チェックも鍵もありません。ログイン画面のチェック「このアプリでログインを維持する」を外せば、そのアプリでは維持しません。
- localStorage に置くのは、「このアプリは維持している」という**目印だけ**（`pwa-remember`）。ログイン画面が自動ログインを試すかの判断に使います。
- **限界**: 端末そのもの（画面ロックのない端末）を盗まれたら、そのアプリは開けます。紛失したら、管理者が「アカウントをロック」するか、本人が別の端末で「他の端末をログアウト」してください。アプリのページに XSS があれば、開いている間は署名を頼めます（鍵そのものは盗めません）。

## 6. 管理者の画面（`/admin/security`）

直近24時間の失敗・成功・ログイン中のセッション数、失敗が多いアドレス／狙われているアカウント、**検知したできごと**（スイーピング・自動ブロック・Cookie使い回し・他サイトからの更新など）、ブロック中のアドレス（解除可）、ロック中のアカウント、アクセスの条件、最近のログイン。すべての操作は監査ログに残ります。

## 7. 2段階認証（パスキー、または パスワード＋2段階認証）

ログインできるのは次のどちらかだけです（管理者がルールを有効にしている間。**既定は有効**）。

| 方法 | 内容 |
|---|---|
| パスキー | 端末の生体認証・PINなど。これだけで完結（2段階認証は不要） |
| パスワード ＋ 2段階認証 | パスワードのあとに、認証アプリの6桁コード（または回復コード）を入力 |

パスワードだけではセッションは作られません（パスワード後〜コード入力までは、5分で切れる署名付きの「引換券」だけが存在します）。

### 流れ
1. **まだ設定していない人**: パスワードの後、そのままログイン画面の中でQRコードを読み取って設定 → 6桁コードで確認 → **回復コード10個**を表示（これを保存して初めてログイン完了）。
2. **設定済みの人**: パスワードの後に6桁コード。「このブラウザを信頼する」にチェックすると、期間中（既定30日）はコードを省略できます。
3. **コードを紛失**: 回復コード（`xxxxx-xxxxx`）を1回だけ使えます。使うと管理者・本人へ通知。回復コードでのログインでは「信頼」は付与されません。

### 守っていること
- TOTP（RFC 6238 / SHA-1 / 6桁 / 30秒、前後1ステップまで許容）。同じコードの**再利用は不可**（使用済みステップを記録）。
- 秘密鍵は暗号化して保存。回復コードは `SESSION_SECRET` で鍵付きハッシュ化して保存し、**同時に2回使っても1回しか成功しません**。
- コード入力は、アカウントごと（15分に5回）・接続元ごと（15分に20回）で制限。超えるとロックの記録と通知が残ります。
- 次の操作で、信頼したブラウザはすべて無効になります: パスワード変更・リセット、アカウントのロック、他の端末のログアウト、2段階認証の解除／リセット。
- 設定の変更（無効化・回復コードの再発行）には、パスワード（と現在のコード）での再確認が必要です。

### 画面
- ユーザー: プロフィール →「2段階認証」（設定／回復コードの再発行／解除）。
- 管理者: `/admin/security` →「ログイン方法」で全員の設定状況（2段階認証・パスキー）を一覧。**リセット**（紛失時。セッションも終了し、次回ログイン時に再設定）。ルールのオン／オフと信頼期間（0日で無効）は「アクセスの条件」から。ルールを切ると警告のできごとが記録されます。

### 導入時の注意
ルールを有効にすると、パスキーを持たない既存ユーザーは**次のパスワードログインで2段階認証の設定を求められます**。

## 環境変数

| 変数 | 意味 |
|---|---|
| `TRUSTED_PROXY_COUNT` | 手前にあるプロキシの台数（既定 1）。誤るとIPが取れず、全リクエストが拒否される（0 も同様） |
| `SESSION_SECRET` | 32文字以上のランダム文字列。本番では必須 |
| `PASSKEY_ALLOW_ANY_ORIGIN` | `1` で、本番でも任意のOriginでパスキーを許可（ngrok等。通常は設定しない） |
| `API_BUDGET_EXEMPT_USER_IDS` | 利用上限の対象外にするユーザーID（カンマ区切り） |
| `SECURITY_REQUIRE_2FA` | 設定キー（画面から変更）。`off` で2段階認証ルールを無効化。E2Eは既定で `off` |
| `SECURITY_REMEMBER_DAYS` | 設定キー（画面から変更）。アプリ（PWA）のログインを維持する日数（既定30・0で無効・最大90） |
| `SECURITY_IDLE_MINUTES` | 設定キー（画面から変更）。操作がないときに自動ログアウトするまでの分数（既定10・0で無効・最大1440） |
| `SECURITY_BLOCK_BOTS` | 設定キー（画面から変更）。`off` でロボットの遮断を無効化（既定はオン） |
| `BOT_BLOCK` | `off` でロボットの遮断を、画面の設定に関わらず全体で無効化 |
| `BOT_ALLOW_UA` | ロボット遮断の例外にする User-Agent の一部（カンマ区切り。監視ツールなど）。E2Eは `Playwright/,HeadlessChrome`（Playwright のAPIクライアントと、手で開くヘッドレスのブラウザ） |
| `SECURITY_CACHE_TTL_MS` | 設定・ブロック一覧をメモリに覚える時間（既定 10〜15秒） |

## 限界（知っておいてください）

- ログインの回数・探索の判定は**メモリ上**です（1台構成が前提）。再起動すると数分の記録は消えます（ログインの失敗回数はDBでも数えるので、そちらは残ります）。複数台にするなら Redis などへの移行が必要です。
- IPの国・ネットワークの判定は外部サービス（ip-api.com）に頼っています。失敗したときは「許可」側に倒れます（利用を止めないため）。
- ロボットの遮断は User-Agent の自己申告が頼りです（上の説明のとおり、偽装には効きません）。
- 端末の識別はCookieです。Cookieを消すと「新しい端末」になります。

## ゼロトラストの観点（毎回の確認・パスワードの入れ直し・セッション切れ→ログイン）

考え方、診断、実装、残りは [35_zero_trust.md](./35_zero_trust.md) にまとめました。要点: ① ページもAPIも、入口で毎回、サーバー側のセッションを確認し、終わっていれば**ログイン画面（戻り先つき）／401**。② 影響の大きい操作は、**直近のパスワード入力**が必要（既定15分）。③ ログイン後の戻り先は、このアプリの中だけ。

## 無操作の自動ログアウト

キーボード・タップ・マウス・スクロールが一定時間（既定10分）ないと、ログアウトになります。管理画面の「セキュリティ → アクセスの条件」で分数を変えられます（0で無効）。

- **画面側**（`src/components/IdleLogout.tsx`）: 本人の操作だけを数えます（画面が自動で行う取得は数えません）。切れる1分前に「ログインを続ける」の確認を出し、時間が来たらログアウトしてログイン画面（`?reason=idle`）へ移ります。同じブラウザの複数タブは操作時刻を共有します（`localStorage`）。
- **サーバー側**: 画面が操作のたびに（30秒に1回まで）`POST /api/auth/activity` を送り、`sessions.last_input_at` を進めます。`getSession()` が、この時刻から（設定の分数＋猶予1分）たったセッションを消します。画面を閉じたまま・ノートPCを閉じたままでも切れ、盗まれたCookieも使えなくなります。切れたあとに「生きてます」を送っても復活しません。
- **ホーム画面のアプリ（PWA）は対象外**: 「ログインを維持する」を選んだアプリは、端末の鍵だけで判断します。無操作でもログアウトしません（画面には `idle_minutes: 0` を返します）。下の「アプリは端末の鍵だけで判断する」を参照。
- E2E は、保存したセッションを長時間APIだけで使うため、既定では無効にしています（`e2e/global-setup.ts`）。`e2e/idle-logout.spec.ts` がオンにして確かめます。
