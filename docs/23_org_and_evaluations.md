# 組織・権限・人事評価

システム管理者が組織（部署・役職・誰がどの部署に入るか）を登録すると、それをもとに **承認の担当** と **人事評価の評価者** が決まります。画面は `/org`（組織）、`/approvals`（チームの承認）、`/evaluations`（人事評価）。メニューでは「組織・人事」「申請・給与」にあります。

## 組織の登録（システム管理者だけ）

部署は自由につくれます（会社 → 部 → 課 のように親子にもできます）。**1人を何個でも部署に入れられ、役職は部署ごとに決めます**（この部署では班長、あの部署では部長）。

| 画面（`/org`） | できること |
|---|---|
| 組織図 | 全員が見られる。**図**（部署のカードを自由に動かせる）と**一覧**を切り替えられる。部署ごとのメンバーと、その部署での役職（上の役職から順に）。複数の部署に所属する人には「兼務」の印 |
| 部署 | 部署の追加・名前変更・移動・削除。**部署ごとに、メンバーを追加し、役職を選び、外せる** |
| 役職と権限 | 役職の追加・編集・削除と、役職ごとの権限。「標準の役職を作成」で 部長・課長・チームリーダー・メンバー を作れる |
| メンバー配置 | 人ごとに、所属する部署と、その部署での役職を並べて編集する（「＋ 部署を追加」「外す」）。選ぶとすぐ反映 |

- 部署を自分の配下に移す（輪になる）ことはできません。配下に部署がある部署は削除できません。空の部署を削除すると、その部署の所属だけが消えます（ほかの部署の所属は残ります。評価票の履歴は、部署なしで残ります）。
- **部署長という設定はありません。** 以前の「部署長」は、役職の権限に置き換わりました（下の「役職に付ける権限」）。
- 変更はすべて監査ログ（`org_*`）に残ります（`org_member_update` には変更前後の所属の一覧が入ります）。メールアドレスと「システム管理者かどうか」は管理者以外には見えません。

### 組織図（図）

PowerPoint の図のように、部署をカードとして好きな場所に動かせます（`src/components/org/OrgDiagram.tsx`。部品は React Flow = `@xyflow/react`。図を開いたときだけ読み込みます）。

- **カードを動かす**: ドラッグで好きな場所へ。離すと位置が保存され（`org_units.pos_x` / `pos_y`、`PUT /api/org/layout`）、全員に同じ配置で見えます。**線（親子）は自動でついてきます。**
- **つなぎ直す**: カードの下の青い丸から、別のカードの上の丸へ線を引くと、そのカードが下の部署になります（`PUT /api/org/units/:id` の `parent_id`）。自分や自分の下の部署の下には、つなげません（輪になるため）。線の真ん中の ✕ で外せます（外した部署は一番上の部署になります）。
- **自動で整列**: 親を子の真ん中の上に置く、整った木の形に並べ直して保存します（`src/lib/org-layout.ts` の `autoLayout`。単体テスト `tests/unit/org-layout.test.ts`）。位置を決めていない部署は、この自動配置の場所に出ます。
- **見る人**: 管理者以外も図は見られ、背景のドラッグで動かし、拡大・縮小もできます。カードを動かす・つなぐ・外す操作は、**システム管理者だけ**です（API もサーバーで管理者を確認します。位置の更新は監査ログ `org_layout_update` に件数だけ残ります）。
- 拡大・縮小は左下のボタン、または Ctrl（Mac は ⌘）＋ホイール。普通のホイールはページのスクロールです。スマホでは、1本指で背景を動かし、2本指で拡大・縮小します。
- テスト: `e2e/org-diagram.spec.ts`。

### 仕組み（`org_memberships`）

- 所属は「人 × 部署 × 役職」の表 `org_memberships`（`user_id`, `unit_id`, `position_id`）です。`PUT /api/org/members/:userId` に `{ "memberships": [{ "unit_id", "position_id" }, …] }` を送ると、その人の所属を**まるごと入れ替え**ます（最大20か所。同じ部署を2回は不可）。
- **役職の権限は、その役職で所属している部署と、その配下の部署に効きます**（`scopeFor`）。たとえば、営業部で「課長」（承認の権限あり）、開発部で「メンバー」なら、営業部（と配下）の人の申請は承認できますが、開発部の人の申請は承認できません。
- 以前の `users.org_unit_id` / `position_id` / `org_units.head_user_id` と、兼務の表は、`20261119000000_org_memberships` の migration で移して消しました。主所属と兼務は、同じ役職でそれぞれの所属になり、**部署長だった人は、その部署のメンバーになります**（これまでの承認・評価の範囲が変わらないように）。

## 経理担当と人事担当（組織に関係なく全社分）

管理者は、勤怠・給与の「管理 › 区分・設定」で、人に **経理担当** と **人事担当** の印を付けられます（管理者だけが変更できます）。どちらも、部署や役職に関係なく、全社分に効きます。

| 印 | できること | できないこと |
|---|---|---|
| **経理担当** | お金まわりの全部: 全員の経費の閲覧と返金、全員の出張の閲覧と手当のマスタ・調整、全員の勤怠の確認と修正、給与明細・報酬の作成と閲覧、業務報告の閲覧、取引先・受取口座の確認、振込申請の閲覧、全銀ファイルの作成と振込済みの記録 | **承認・却下**（経費・出張・振込申請）、**全銀の設定**（会社の口座・委託者コード。値は管理者だけに見える）、組織・ユーザー・メールボックスなど管理画面の設定、区分や担当の印の変更 |
| **人事担当** | 全員の人事評価の閲覧、評価期間の作成・開始・確定・終了、評価者の変更、差し戻し（役職の「人事評価を運用する」と同じ） | 評価以外（経費・給与・勤怠など） |

- 人事は、役職に「人事評価を運用する」権限を付ける方法でも、これまでどおり決められます（部署長でなくても全社に効きます）。印は、役職や部署を割り当てなくても人事にしたいとき用です。
- 印の変更は監査ログ（`accounting_role_update`・`hr_role_update`）に残ります。

役職に付ける権限:

| 権限 | できること |
|---|---|
| 部下の経費・出張を承認する | この役職で所属している部署（配下を含む）のメンバーの経費・出張を承認・却下できる |
| 部下の人事評価をする | この役職で所属している部署のメンバー（自分より下の役職）の評価者になる |
| 人事評価を運用する | 評価期間の作成・開始・確定・終了と、全員の評価の閲覧（部署に関係なく全社） |

- 「部下の…」は **その役職で所属している部署（と配下）にだけ** 効きます。同じ人でも、権限のない役職（メンバーなど）で所属している部署では、何もできません。
- 2つの部署に所属する人の申請は、**どちらの部署の承認者も承認できます**（先に処理した方で完了）。承認待ちの一覧も、申請の通知（Mattermost）も、両方の承認者に届きます。
- 自分の申請は承認できません（上の部署の承認者、または管理者が承認します）。
- 役職の権限を変えると、**その役職の全員に今すぐ** 反映されます。異動（所属の変更）も同様です。
- 返金・振込・給与・口座の確認など、**別の権限は増えません**（これらは上の「経理担当」の印で決まります）。システム管理者は常にすべてできます。

### チームの承認（`/approvals`）
担当範囲の承認待ちの経費・出張を一覧し、承認／却下（理由必須）できます。管理者には全員分が出ます。申請が出ると、申請者の所属する各部署（と、その上の部署）で承認の権限を持つ人と、管理者に Mattermost で通知されます（本人には届きません）。

## 人事評価

流れ: **準備中 → 評価中 → 終了**。評価中の1人1票は **自己評価 → 上長評価 → 確定（人事）** と進みます。

1. **人事**（管理者、または「人事評価を運用する」権限の人）が評価期間を作る: 期間と評価項目（項目ごとに説明と重み 1〜10）。開始前なら編集・削除できる。
2. **開始** すると全員分の評価票ができ、全員に通知。**評価票は、所属する部署ごとに1枚**です（2つの部署に所属する人には2枚。それぞれ評価者が違い、自己評価・上長評価・確定も部署ごと）。**評価者**は、その部署で「評価する」権限を持つ人のうち、**本人の役職より1つ上（序列がいちばん近い上）の人**から自動で決まる（`evaluatorFor`）。その部署に上の人がいなければ、上の部署で評価の権限を持ついちばん序列の高い人。同じ序列が複数いるときは、いつも同じ人（ID順）。どの部署にも所属しない人には、評価者なしの1枚ができ、人事が個別に設定する。
3. **自己評価**: 本人が各項目に 1〜5 点とコメント。下書き保存でき、提出すると固定される。
4. **上長評価**: 自己評価が提出されると評価者が評価できる。評価者は本人の自己評価を見ながら点数をつけ、提出すると固定される。
5. **確定**: 人事が結果を確定して公開する。総合点＝上長の点数の **重みつき平均**（5点満点）、等級は S ≥ 4.5 / A ≥ 3.5 / B ≥ 2.5 / C ≥ 1.5 / D。人事は等級を変更できる（**理由のコメントが必須**で、本人にも表示される）。
6. 全員確定したら期間を **終了**（未確定があるときは確認が出る）。

### 誰に何が見えるか
- **本人**: 自分の自己評価。上長の点数・コメント・結果は **確定するまで見えない**。
- **評価者**: 自己評価が提出されてから本人の欄が見える。確定前の結果（総合点・等級）は見えない。
- **人事**: すべて。
- それ以外の人は評価票を開けません（403）。

### 人事の操作
- **評価者の変更**（評価できる人だけが選べる。本人は選べない）。
- **差し戻し**: 提出済みの自己評価／上長評価を戻して書き直させる（自己評価を戻すと上長の提出も戻る）。確定後はできない。
- **自分の評価は確定できない**（他に確定できる人がいる限り）。

### 通知（Mattermost。点数・等級は載せません）
開始 → 全員 / 自己評価の提出 → 評価者 / 上長評価の提出 → 人事 / 確定 → 本人。

## セキュリティ
- 組織・役職・権限の変更はシステム管理者だけ。評価期間の操作は人事だけ。すべてサーバー側で確認し、監査ログに記録。
- 承認の権限判定は `src/lib/org-server.ts`（`canReviewUser`）の1か所。経費・出張の承認APIがこれを使う。
- 評価の閲覧範囲は `src/lib/eval-server.ts`（`serializeEvaluation`）で一括してマスクする。単体テスト `tests/unit/eval-visibility.test.ts`。
- 同時操作: 期間の開始・確定は条件つき更新で1回だけ成功する。
