# 意味検索（Embedding）

メール一覧の検索に「**意味でも探す**」を足しました。言葉が同じでなくても、内容が近いメールを見つけます（例: 「インボイス」で探すと、「請求書の送付」「代金のお振込のお願い」が出る）。

**初期状態は無効**です。`EMBEDDING_PROVIDER=local`（サーバー内のモデル）か `EMBEDDING_API_URL`（外部サービス）を設定したときだけ、検索欄の下に「意味でも探す」のスイッチが出ます。

## 画面での見え方

- 検索すると、これまでどおり**言葉が含まれるメール**が日付順に並びます。
- その下に「**意味が近いメール**」の区切りが入り、言葉は含まれないが内容が近いスレッドが、近い順に（最大20件）並びます。件名の横に「意味」の印が付きます。
- `from:` `status:` など絞り込みは意味検索にも効きます（言葉の部分だけが意味で探されます）。
- スイッチを切るとキーワード検索だけに戻ります。この選択はブラウザごとに覚えます。
- 意味検索のサービスが落ちていても検索は止まりません。キーワードの結果だけを出し、「意味検索を一時的に使えません」と知らせます。

## 設定

ベクトルを作る方法は2つあります。**ベクトルどうしの比較（内積）は、どちらの場合もこのアプリの中で計算します**。違うのは「文章をベクトルにするモデル」をどこで動かすかだけです。

### A. 自分のサーバーで動かす（おすすめ・メールが外に出ない）

```
EMBEDDING_PROVIDER="local"
```

- 小さな多言語モデル（既定 `Xenova/multilingual-e5-small`、384次元、日本語対応）を、このアプリのプロセス内で動かします（transformers.js + onnxruntime-node）。API キーも外部への通信も要りません。
- **初回だけ**Hugging Face からモデル（8ビット版で約120MB）をダウンロードして `storage/models/`（`EMBEDDING_CACHE_DIR` で変更可）に保存します。以降は読み込むだけです。
- インターネットに出られないサーバーでは、モデルのファイルを先に同じ場所へ置き、`EMBEDDING_LOCAL_ONLY=1` を付けるとダウンロードを禁止できます。
- 本番ビルド（standalone）には、Linux 用のネイティブライブラリ（約70MB。GPU 用は除外）を含めています。Mac / Windows は開発用で、本番の Docker（Linux）が前提です。

### B. 外部のサービスを使う

OpenAI 互換の `POST {EMBEDDING_API_URL}/embeddings` を話すサービスなら何でも使えます（OpenAI・Voyage・Azure、自前の Ollama / text-embeddings-inference など）。`EMBEDDING_API_URL` があれば A より優先されます。

| 環境変数 | 意味 | 既定 |
|---|---|---|
| `EMBEDDING_PROVIDER` | `local` でサーバー内のモデルを使う | なし |
| `EMBEDDING_API_URL` | 例 `https://api.openai.com/v1`。**A も B も指定しなければ機能ごと無効** | なし |
| `EMBEDDING_API_KEY` | あれば `Authorization: Bearer` で送る（B） | なし |
| `EMBEDDING_MODEL` | モデル名 | A: `Xenova/multilingual-e5-small` / B: `text-embedding-3-small` |
| `EMBEDDING_DIMENSIONS` | 次元数を指定できるモデル用（B。小さいほど軽い。例 512） | モデルの既定 |
| `EMBEDDING_CACHE_DIR` / `EMBEDDING_LOCAL_ONLY` | A のモデルの置き場所／ダウンロード禁止（`1`） | `storage/models` / 許可 |
| `EMBEDDING_MIN_SCORE` | 「近い」とみなす類似度の下限（0〜1）。ノイズが多ければ上げる | `0.3` |
| `CRON_SECRET` | `/api/cron/embeddings` の呼び出し用の鍵 | なし |

`e5` を含む名前のモデルには、検索語に `query: `、メールに `passage: ` を自動で付けます（このモデル群の決まりです）。

**モデルを変えると、次のインデックス作成で全スレッドが作り直されます**（モデルごとにベクトルの意味が違うため）。E5 系は類似度が全体に高めに出ることがあるので、実際のメールで見て `EMBEDDING_MIN_SCORE` を調整してください。

## しくみ

1. **スレッドごとに1つのベクトル**を作ります。入力は「件名＋新しい3通の本文（引用行を除く・合計2000文字まで）」。添付ファイルの中身は含みません。
2. 作るのは**バックグラウンド**です。メール同期の定期処理（`instrumentation.node.ts` の `tick`）が、まだ無い／メールが増えたスレッドを新しい順に50件ずつ処理します。手動・外部のスケジューラからは `GET /api/cron/embeddings`（`Authorization: Bearer $CRON_SECRET`）。`pending` が 0 になるまで繰り返し呼べます。
3. ベクトルは `thread_embeddings` に float32 の BYTEA で保存します（長さ1に正規化済み。内積＝類似度）。スレッドを消すと一緒に消えます。
4. 検索時は、その人が**見られるスレッド**（`buildThreadsWhere` の権限条件）の中だけでベクトルを比べます。見られないメールボックスのスレッドは、意味が近くても出ません。
5. 検索語のベクトルは、同じ言葉なら100件までメモリに覚えます（個人メールと共有メールの2回分の問い合わせで、サービスを1回しか呼ばないため）。

## デメリット・注意

- **（外部サービス B を使う場合）メールの文章がそのサービスに送られます。** 件名と本文の一部が渡ります。社外秘が多いなら A（サーバー内で動かす）か、自社内の Ollama などを選んでください。
- **（A の場合）サーバーの負担が増えます。** モデルの読み込みでメモリを数百MB使い、ベクトル作成は CPU を使います。最初の既存メールの取り込みは時間がかかります（数千スレッドで数分〜十数分の見込み。実測はしていません）。初回の検索（モデル読み込み）は数秒遅くなります。Docker イメージも約70MB 大きくなります。
- **（B の場合）費用がかかります。**スレッド1件あたりは数百〜2000文字なので、`text-embedding-3-small` なら1万スレッドで数十円〜数百円の目安です。最初の1回（既存メールの取り込み）と、新着メールごとに発生します。
- **反映に少し遅れます。** 新着メールは、次の定期処理（既定3分）までは意味検索に出ません（キーワード検索にはすぐ出ます）。
- **ノイズが出ます。** 「近い」は確率的な判断なので、関係の薄いメールが混ざったり、逆に探しているものが出なかったりします。だから「言葉が一致した結果が上、意味は下に足す」形にし、スイッチで切れるようにしています。固有名詞・型番・メールアドレスの完全一致は、キーワード検索のほうが確実です。
- **検索が少し遅くなります。** 検索のたびに検索語を1回ベクトル化します（B は通信が入ります）。ベクトルの比較は、見られる全スレッドを読み込んでアプリ側で計算するため、スレッドが**数万件を超える**あたりから重くなります。そこまで増えたら、PostgreSQL の `pgvector`（近似最近傍の索引）への移行を検討してください。
- **検索範囲は「スレッド単位」です。** 1つのスレッドに1つのベクトルなので、長いやりとりの途中の話題や、古い返信の内容は拾いにくくなります。新しい3通が中心です。
- **日本語の精度はモデル次第です。** 多言語対応のモデルを選んでください。
- **サービスの停止時（A ではモデルを読み込めないとき）は、新しいメールがインデックスされません**（検索は動きます）。復旧すれば次の定期処理で追いつきます。
